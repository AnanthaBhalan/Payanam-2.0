feat(phase6): replace Ray Client with the Ray Job REST API + Redis handoff

Removes Ray Client from the Temporal path entirely. Ray Client binds its
session to the calling thread and is not task or thread safe, so every
submission from a temporal activity failed with "AttributeError:
InProgressSentinel object has no attribute id". Ray Jobs are the supported
integration path for an external orchestrator such as Temporal.

Flow
----
app/solver/job_entrypoint.py -- the standalone script the cluster runs. It
parses --task-id and a base64 payload, calls ray.init(address="auto") to get a
local (in-cluster) context, runs the CP-SAT solve, writes the itinerary to
Redis at payanam:solve_result:{task_id} with a 600s TTL, and exits.

app/solver/ray_dispatch.py -- repurposed. submit_solve_job POSTs to
/api/jobs/; wait_for_solve_result polls /api/jobs/{id} with bounded backoff and
reads the Redis key on SUCCEEDED. Imports no ray at all.

solve_itinerary activity -- rewritten to use httpx plus Redis. No ray import
happens in the worker. Submission and job failures raise ApplicationError so
the Saga handles them, and the handoff key is deleted in a finally block.

/health now asks the Ray dashboard (GET /api/version) instead of starting a
client or dispatching a probe task.

Image work (Dockerfile.ray)
--------------------------
* The stock rayproject/ray image has no ortools, so a job cannot solve;
  runtime_env pip installs proved unreliable, so ortools and redis are baked
  into the image along with the app at /opt/payanam.
* numpy 2.x is ABI-incompatible with the pyarrow in that image
  ("AttributeError: _ARRAY_API not found"), which crashed the ray CLI that Ray
  Jobs uses to launch work. Pinning numpy<2 -- after the ortools install,
  which otherwise pulls numpy>=2 back in -- makes "ray --version" work.

Verified
--------
The dashboard is reachable over REST and job submission is accepted. The
entrypoint, run directly inside the cluster, completes the whole handoff:
it solved the demo circuit and wrote feasible=True to
payanam:solve_result:probe123 with the 600s TTL.

NOT yet achieved, stated plainly: a job submitted through /api/jobs/ still
ends FAILED with no captured logs, so the end-to-end Temporal -> job -> Redis
-> itinerary path has not completed in a single run. Every component is proven
individually; what remains is diagnosing why Ray's job supervisor reports no
logs for the submitted entrypoint. tests/test_ray_jobs.py asserts the full
handoff and currently fails on exactly that step, skipping cleanly when the
dashboard or Redis is absent.
